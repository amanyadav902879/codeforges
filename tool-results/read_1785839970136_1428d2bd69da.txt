     7→     7→1. Executive Summary
     8→     8→CodeForge ULTRA PRO MAX is not a learning platform. It is a living developer ecosystem that simulates real-world software engineering — complete with consequences, team dynamics, system failures, security breaches, and AI teammates — while teaching Java, Spring Boot, full-stack development, and AI/ML from zero to production-grade. Every feature exists to answer one question: "How do we make learning so addictive that skipping a day feels wrong?"

    75→    75→1.2.1 Path Structure
    76→    76→Path → Module → Lesson → Concept → Exercise → Challenge → Project
    77→    77→Each path is a Directed Acyclic Graph (DAG), not a linear list — parallel tracks exist
    78→    78→Example: After "Java Fundamentals," user can simultaneously pursue "Spring Boot" AND "DSA" — or pick one

    81→    81→Performance scoring per lesson (accuracy, time taken, hints used, attempts)
    82→    82→Weak area detection: if user scores <60% on "Collections," engine auto-injects 2-3 remedial lessons
    83→    83→Strong area fast-forward: if user scores >95% on "OOP Basics," next related lesson marked as "challenge available — pass to skip"
    84→    84→Path morphing: the path shape changes per user — no two users see identical path sequence
    85→    85→"Review ahead" feature: user can peek at upcoming lessons (read-only, no exercises) to plan their week

    87→    87→Every lesson has three versions the user can switch between at any time:
    88→    88→
    89→    89→EXPLAIN LIKE I'M 5 — Analogies, visual diagrams, no jargon, extra hints in exercises
    90→    90→STANDARD — Normal technical explanation, moderate hints
    91→    91→EXPERT — Minimal explanation, assumes prior knowledge, no hints, harder test cases, time limits
    92→    92→1.2.4 Real-World Context Wrappers
    93→    93→Every lesson is framed inside a realistic scenario, not taught in isolation:
    94→    94→
    95→    95→"HashMap" is not taught as "a key-value data structure" — it's taught as "You're building a session store for 10 million users and need O(1) lookups"
    96→    96→"Spring Security" is not "add this dependency" — it's "Your API is getting DDoS'd and someone is scraping user data — fix it"
    97→    97→Context makes the "why" undeniable — user never asks "but when will I use this?"

   228→   228→1.7 Code Execution Sandbox
   229→   229→1.7.1 Sandbox Architecture
   230→   230→Each code execution spawns an isolated Docker container with:
   231→   231→Resource limits: 512MB RAM, 1 CPU core, 10-second execution timeout, 50MB disk
   232→   232→Network disabled (no outbound connections from user code)
   233→   233→No access to host filesystem
   234→   234→Process killed if exceeds limits
   235→   235→Container pool for warm starts — pre-spawned containers reduce cold-start latency to <500ms
   236→   236→Container recycling after each execution (no state leakage between runs)
   237→   237→1.7.2 Execution Flow
   238→   238→User clicks "Run" → code + dependencies sent to execution service → container selected from pool → code compiled → executed → stdout/stderr captured → container killed/recycled → results sent back via WebSocket
   239→   239→For debugging: container stays alive, WebSocket keeps connection open for breakpoint interactions
   240→   240→Max 3 concurrent containers per user (prevents resource abuse)
   241→   241→1.7.3 Security Measures
   242→   242→seccomp profile restricting system calls (no fork, no exec, no network sockets)
   243→   243→gVisor runtime option for defense-in-depth (kernel-level isolation)
   244→   244→Execution logs archived for 7 days (for debugging sandbox issues, not for spying on users)
   245→   245→Rate limiting: max 60 executions per hour per user

   778→   778→6.9 Security (Non-Auth)
   779→   779→6.9.1 Application Security
   780→   780→Input sanitization: All user input sanitized — SQL parameters (never string concatenation), HTML escaping, XSS prevention
   781→   781→CORS: Strict origin whitelist for API
   782→   782→CSP: Content Security Policy headers preventing inline script execution
   783→   783→Rate limiting: Per-endpoint, per-user rate limits (Spring Boot + Bucket4J)
   784→   784→Request validation: All API inputs validated with Bean Validation (jakarta.validation)
   785→   785→HTTP headers: HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy
   786→   786→Dependency scanning: OWASP Dependency-Check in CI/CD pipeline
   787→   787→Secrets management: Environment variables + vault (HashiCorp Vault or AWS Secrets Manager)
   788→   788→6.9.2 Sandbox Security (Critical)
   789→   789→Containers run with non-root user
   790→   790→seccomp profile blocking: clone, execve, mount, ptrace, keyctl
   791→   791→No network access (except for specific LLM integration exercises, which use a separate, heavily restricted network namespace)
   792→   792→No access to host filesystem, no access to other containers
   793→   793→Resource limits enforced at Docker level (not just application level)
   794→   794→Container escape monitoring: alert if any container attempts unexpected syscalls
   795→   795→Execution logs retained for forensic analysis if needed
   796→   796→6.9.3 AI Security
   797→   797→Prompt injection detection: user code/comments scanned for prompt injection before sending to AI API
   798→   798→AI responses filtered: never expose system prompts, never execute AI-suggested code on host
   799→   799→API key rotation: Claude API key rotated monthly
   800→   800→Token usage budget: per-user daily token limit (prevent cost runaway)
   801→   801→AI response caching: identical questions within 24 hours return cached response (saves tokens)
