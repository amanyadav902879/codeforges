1. Executive Summary
CodeForge ULTRA PRO MAX is not a learning platform. It is a living developer ecosystem that simulates real-world software engineering — complete with consequences, team dynamics, system failures, security breaches, and AI teammates — while teaching Java, Spring Boot, full-stack development, and AI/ML from zero to production-grade. Every feature exists to answer one question: "How do we make learning so addictive that skipping a day feels wrong?"

This PRD represents the complete, unabridged, no-compromises vision. Every feature listed here is technically buildable. Prioritization is handled via phases — but nothing is deleted.

1.1 Authentication & Identity System
1.1.1 Auth Methods
Passkey-First Authentication — WebAuthn/FIDO2 as primary login method (no password needed)
Password + TOTP — Traditional fallback with time-based one-time password via authenticator app
Magic Link — Passwordless email login for quick access
OAuth2/OIDC — GitHub, Google, Discord login with granular scope selection screen
Biometric WebAuthn — Fingerprint/face recognition on supported devices
1.1.2 Adaptive Risk Engine
Device fingerprinting on every request — unknown device triggers step-up auth
Geographic anomaly detection — impossible travel = instant lock + email alert
Time-of-day anomaly — 3 AM login when user never logs in at night = extra verification
Behavioral biometrics baseline — typing cadence, mouse movement patterns stored as fuzzy hash
Risk score computed per request: LOW (allow) → MEDIUM (log) → HIGH (require MFA) → CRITICAL (deny + alert)
All decisions logged in immutable audit trail
1.1.3 Session Management
JWT access tokens (15-minute TTL) + rotating refresh tokens (7-day TTL, one-time use)
Token binding to device fingerprint — stolen token useless on different device
Concurrent session control — user can see and terminate all active sessions
"Kill Switch" — one-click revoke all sessions across all devices
Session heatmap visible to user — "You logged in from these locations this month"
1.1.4 Role & Permission System
Role hierarchy: SUPER_ADMIN → ADMIN → MODERATOR → MENTOR → LEARNER → GUEST
Permission granularity: not just "can edit lessons" but "can edit lessons in paths where they are assigned as mentor"
Role assignment audit log — who assigned what role, when, why
Temporary role elevation — "become moderator for 24 hours" for specific events
1.1.5 Profile System
Avatar (upload + auto-generated pixel art avatar based on username hash)
Bio, location, website links (GitHub, LinkedIn, Twitter, personal site)
Skill tags (auto-suggested based on completed lessons, manually adjustable)

1.2 Living Learning Paths
1.2.1 Path Structure
Path → Module → Lesson → Concept → Exercise → Challenge → Project
Each path is a Directed Acyclic Graph (DAG), not a linear list — parallel tracks exist
Example: After "Java Fundamentals," user can simultaneously pursue "Spring Boot" AND "DSA" — or pick one
Prerequisite enforcement via graph traversal — cannot access node until all parent nodes completed (or challenge-passed)
1.2.2 Adaptive Path Engine
Performance scoring per lesson (accuracy, time taken, hints used, attempts)
Weak area detection: if user scores <60% on "Collections," engine auto-injects 2-3 remedial lessons
Strong area fast-forward: if user scores >95% on "OOP Basics," next related lesson marked as "challenge available — pass to skip"
Path morphing: the path shape changes per user — no two users see identical path sequence
"Review ahead" feature: user can peek at upcoming lessons (read-only, no exercises) to plan their week
1.2.3 Difficulty Tiers Per Lesson
Every lesson has three versions the user can switch between at any time:

EXPLAIN LIKE I'M 5 — Analogies, visual diagrams, no jargon, extra hints in exercises
STANDARD — Normal technical explanation, moderate hints
EXPERT — Minimal explanation, assumes prior knowledge, no hints, harder test cases, time limits
1.2.4 Real-World Context Wrappers
Every lesson is framed inside a realistic scenario, not taught in isolation:

"HashMap" is not taught as "a key-value data structure" — it's taught as "You're building a session store for 10 million users and need O(1) lookups"
"Spring Security" is not "add this dependency" — it's "Your API is getting DDoS'd and someone is scraping user data — fix it"
Context makes the "why" undeniable — user never asks "but when will I use this?"
1.2.5 Path Versioning
Every path has a semantic version (e.g., "Java Fundamentals v3.2.1")
Changelog visible: "v3.2 added lesson on Records, updated exercise test cases for Java 21"
Users who started on v3.0 can continue on v3.0 OR migrate to v3.2 (with diff shown)
Deprecated lessons archived but accessible — "This lesson was replaced by X, but you can still view it"

1.4.2 Test Case Architecture
Each exercise has: public test cases (visible to user) + hidden test cases (revealed only after submission)
Hidden tests cover: edge cases, large inputs, null inputs, concurrent access, error conditions
Test case tagging: @Smoke, @EdgeCase, @Performance, @Concurrency, @Security
After pass: user sees which hidden tests existed (but not their code) — learning through test discovery
After fail: user sees which test category failed (e.g., "Your solution fails on edge cases") without revealing the exact test
1.4.3 Feedback System
Instant pass/fail with execution time and memory usage
Failure hints — progressive: 1st fail = category hint, 2nd fail = specific hint, 3rd fail = partial solution reveal
Performance feedback — "Correct, but your solution is O(n²). Can you do O(n)?" (if optimal solution exists)
Style feedback — "Works, but consider using Stream API here" (non-blocking suggestion)
Comparison — "Your solution used 15 lines. The community median is 8 lines." (motivation, not shaming)
1.4.4 Anti-Cheat Measures
Code similarity detection across all submissions (MOSS-style) — flag but don't auto-punish
Copy-paste detection — if user pastes code from outside, log it (not block — sometimes legitimate)
Time anomaly detection — solved in 3 seconds? Flag for review
Submission frequency limiting — max 10 submissions per minute per exercise

1.7 Code Execution Sandbox
1.7.1 Sandbox Architecture
Each code execution spawns an isolated Docker container with:
Resource limits: 512MB RAM, 1 CPU core, 10-second execution timeout, 50MB disk
Network disabled (no outbound connections from user code)
No access to host filesystem
Process killed if exceeds limits
Container pool for warm starts — pre-spawned containers reduce cold-start latency to <500ms
Container recycling after each execution (no state leakage between runs)
1.7.2 Execution Flow
User clicks "Run" → code + dependencies sent to execution service → container selected from pool → code compiled → executed → stdout/stderr captured → container killed/recycled → results sent back via WebSocket
For debugging: container stays alive, WebSocket keeps connection open for breakpoint interactions
Max 3 concurrent containers per user (prevents resource abuse)
1.7.3 Security Measures
seccomp profile restricting system calls (no fork, no exec, no network sockets)
gVisor runtime option for defense-in-depth (kernel-level isolation)
Execution logs archived for 7 days (for debugging sandbox issues, not for spying on users)
Rate limiting: max 60 executions per hour per user

4.1.1 How It Works

4.1.2 Review Categories
Category
What AI Checks
Correctness	Logic errors, off-by-one, null handling, edge cases missed
Performance	Time complexity, unnecessary iterations, memory allocation patterns
Java Idioms	Not using streams where appropriate, not using try-with-resources, boxing/unboxing issues

6.9 Security (Non-Auth)
6.9.1 Application Security
Input sanitization: All user input sanitized — SQL parameters (never string concatenation), HTML escaping, XSS prevention
CORS: Strict origin whitelist for API
CSP: Content Security Policy headers preventing inline script execution
Rate limiting: Per-endpoint, per-user rate limits (Spring Boot + Bucket4J)
Request validation: All API inputs validated with Bean Validation (jakarta.validation)
HTTP headers: HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy
Dependency scanning: OWASP Dependency-Check in CI/CD pipeline
Secrets management: Environment variables + vault (HashiCorp Vault or AWS Secrets Manager)
6.9.2 Sandbox Security (Critical)
Containers run with non-root user
seccomp profile blocking: clone, execve, mount, ptrace, keyctl
No network access (except for specific LLM integration exercises, which use a separate, heavily restricted network namespace)
No access to host filesystem, no access to other containers
Resource limits enforced at Docker level (not just application level)
Container escape monitoring: alert if any container attempts unexpected syscalls
Execution logs retained for forensic analysis if needed
6.9.3 AI Security
Prompt injection detection: user code/comments scanned for prompt injection before sending to AI API
AI responses filtered: never expose system prompts, never execute AI-suggested code on host
API key rotation: Claude API key rotated monthly
Token usage budget: per-user daily token limit (prevent cost runaway)
AI response caching: identical questions within 24 hours return cached response (saves tokens)
